# CLAUDE.md — AlimaProspects

Root instructions for Claude Code (and humans). Read this first, every session.

AlimaProspects is a multi-tenant SaaS that helps businesses find, qualify and contact prospects with AI (web + mobile). See `docs/architecture.md` for the system map and `mvp.md` for the phased build plan.

---

## 0. Golden rules

- **Never commit secrets.** Never weaken tenancy scoping, transactions, or tests to make something pass.
- **Claude must never run `migrate:fresh`, `migrate:refresh`, `migrate:reset` or `db:wipe`.** The local dev database is **MySQL `alima_prospects`** and holds real records; these commands drop every table. Apply schema changes with `php artisan migrate` only (a rework gets a new corrective migration). For Claude this is enforced in `.claude/settings.json` — `deny` permission rules plus a `PreToolUse` hook (`.claude/hooks/block-destructive-migrations.cjs`) — so Claude cannot run them even when asked; the correct response to such a request is to tell the user to run it themselves. **The user runs these freely in their own terminal** (the app-level `DB::prohibitDestructiveCommands()` guard is production-only, by design, so local rebuilds are not hindered). Tests are unaffected — they use an in-memory SQLite, and that is now **enforced at runtime**: `AppServiceProvider::configureDefaults()` throws if a test process boots on any driver but SQLite, because `RefreshDatabase` runs its own `migrate:fresh` that no permission rule or hook can see, and phpunit.xml's pins lose to a variable exported in the shell. For the same reason the one test that does drop MySQL tables (`SignalsMysqlDialectTest`) only runs against a schema whose name ends in `_test`.
- If a requirement is unclear or conflicts with these rules, **stop and ask**.
- A phase is **not complete** until: `composer test` green, `composer analyse` clean (Larastan ≥ level 6; repo is at **7**), frontend `npm run check` + `npm run types:check` + `npm run build` pass, and **docs are updated**.
- **The brand is law (see §2a).** Any UI — web or mobile — must obey the Alima brand defined in the two source PDFs. Do not invent colours, type, spacing, logo treatment or tone.

## 2a. Brand — the source of truth (read before ANY frontend work)

The authoritative brand lives in **two PDFs**, both in **`.claude/docs/brand/`** (originals) and mirrored in **`docs/brand/`**:

- **`Alima — Brand Guidelines.pdf`** — the full 67-page system: logo, colour, typography, elements, voice, digital tokens, print.
- **`Alima.pdf`** — the companion brand file.

Before building or changing any screen, component, email, or mobile view:

1. **Read `docs/brand/brand-tokens.md`** — the engineering extraction of the PDFs (palette with hex, semantic digital tokens, type scale, radius/shadow/motion, spacing/grid, logo rules, voice). If a detail you need isn't there, **open the PDFs** and, if useful, extract more into `brand-tokens.md`.
2. **Build with tokens, never raw hex.** Colours/type/spacing come from the Tailwind `@theme` tokens (encoded in Phase 2 from `brand-tokens.md`), not hand-picked values.
3. **Obey the non-negotiables:** lead with Cloud Cream, one hero accent per layout; **Signal Orange is decorative only — never a status colour** (use `status.*`); Poppins (Latin) / Tajawal (Arabic) / DM Mono (labels); logo clear-space, min-sizes and approved colourways; WCAG AA; **EN/AR + RTL**; brand voice (bright, bold, clear, together) for all copy.
4. **When in doubt:** fewer colours, more cream, a bigger logo — then ask. Anything not covered by the PDFs is flagged for brand-owner approval (see `brand-tokens.md §7`), never silently invented.

Changes to brand interpretation are recorded in `brand-tokens.md`; the PDFs themselves are the fixed reference.

## 2. Architecture rules (non-negotiable)

### Structure — domain modules (ADR 0002)

Code lives under `app/Modules/<Module>/` with: `Actions/ Services/ Contracts/ Data/ Enums/ Events/ Listeners/ Jobs/ Models/ Policies/ Support/ Observability/ Http/{Controllers/Web, Controllers/Api/V1, Requests, Resources}/ Exceptions/ routes/{web,api}.php Providers/<Module>ServiceProvider.php`. (`Support/` is small collaborators that are neither an Action nor a Service; **`Observability/`** is code whose job is to report what the module is doing and which could be deleted with the product still working — a Pulse recorder is not a `Listeners/` listener for that reason. Both are explained in ADR 0002.) Migrations/factories/seeders stay in standard Laravel dirs but are **named by module**. Tests in `tests/Feature/<Module>` + `tests/Unit/<Module>`. Frontend in `resources/js/Pages/<Module>/` + `resources/js/Components/<Module>/`. Each module has a `<Module>ServiceProvider` registered via the Core base provider.

### Code rules

- **Thin controllers:** authorise (Policy) → validate (FormRequest) → call **one** Action/Service → return (Inertia page or API Resource). No queries, no business logic, no try/catch soup in controllers.
- **Actions** = single operations (`CreateLeadAction`). **Services** = orchestration / third-party integrations. Pass DTOs in, return models/DTOs out.
- **All writes in `DB::transaction()`** at the Action level. Post-commit work (jobs, events, emails, external calls) uses `DB::afterCommit()` / `afterCommit`. **Never call external APIs inside a transaction.**
- **Multi-tenancy (ADR 0006):** every tenant table has `team_id`. Use the `BelongsToTeam` trait (global scope + auto-assign). **Policies double-check ownership.** Every tenant model needs a test proving cross-tenant access fails.
- **Logging:** structured + contextual (`Log::withContext(['team_id','user_id','request_id'])`); a channel per module where one earns it — `ai`, `lead_sourcing`, `signals`, `outreach`, `notifications`, `insights`, `billing` (add yours to `config/logging.php` and say so in the module doc). **Never log secrets or full personal data — log IDs.**
- **Errors:** domain-specific exceptions per module (extend `App\Modules\Core\Exceptions\DomainException`), rendered centrally in `bootstrap/app.php`. Friendly to users; details to logs/Sentry. External calls use timeouts, retries w/ backoff, circuit-breaker guards.
- **Jobs:** idempotent; `ShouldBeUnique` where duplicates harm; set `$tries`, `$backoff`, `$timeout`; implement `failed()`. Long AI/lead jobs report progress over Reverb.
- **Validation** only in FormRequests/Data. **Authorisation** only in Policies/Gates. **Compliance
  gating is neither** — whether a lead may be approached is `Outreach\Services\OutreachGuard`'s
  answer, not a policy's: authorisation asks whether this member may act, the guard asks whether this
  prospect may be approached, and conflating them means a legal rule enforced by a role check.
- **Never notify directly.** Raising a notification is
  `Notifications\Services\NotificationDispatcher` (`send` / `toTeam` / `toAdmins`) — never Laravel's
  facade, never `$user->notify()`. The dispatcher is what resolves the member's per-team channel
  preferences, stamps `team_id` on the row, drops members who have left, and keeps the stored payload
  free of prose (keys + params, never a sentence). A notification that would fan out per record needs
  **aggregating** first — see `AnnounceTopLeadsJob` for the pattern.
- **Anything that reaches a prospect goes through Outreach.** Suppression, sender identification and
  the opt-out are conditions of sending, not features of a screen (`docs/compliance.md` §3.2–3.3).
- **Enums** for every status/type column. **No magic strings.**
- **Money** = integer minor units. **Timestamps** UTC in DB, displayed in team timezone.
- **Strict types** (`declare(strict_types=1);`) in every PHP file; typed properties + return types everywhere.
- **Eloquent:** `Model::shouldBeStrict()` outside production; avoid N+1 (eager load; test with `preventLazyLoading`).
- **API:** versioned `/api/v1`, **API Resources only** (never return models), consistent error envelope, pagination, per-token rate limiting. Since **Phase 17** each of those is a property of _every_ endpoint, asserted over the whole route table in `tests/Feature/Api/V1/RouteContractTest.php` — a new route must be declared by its own module (`routes/api.php` is deliberately empty), named, behind `auth:sanctum`, scoped with an `ability:` from `Auth\Enums\TokenAbility`, and present in `docs/api/openapi.json`. The error envelope has one definition, `Core\Http\Responses\ApiError`; a module adds a failure mode by extending `DomainException` with its own code, never by inventing a response shape. Scoped **by path** (`api/*`), because the web forms depend on Laravel's native 422 for their error bags. `per_page` comes from `Core\Http\Requests\PaginatedIndexRequest`.
- **Frontend:** **obey the brand (§2a)** — the two PDFs in `.claude/docs/brand/` + `docs/brand/`, via `docs/brand/brand-tokens.md`. Brand tokens as Tailwind theme vars, never raw hex; build reusable base components (`Button`, `Input`, `Card`, `Table`, `Modal`, `Badge`, `EmptyState`, `Toast`) before feature screens; responsive + accessible (WCAG AA, keyboard nav, labels); **EN/AR + RTL** (ADR 0007). Signal Orange is decorative only, never a status colour.
- **Tests:** every Action has a unit/feature test; every endpoint has a feature test covering auth, validation, tenancy and happy path. **Fake external providers** (AI, lead sources, Stripe) in tests.

## 3. Where things live

- `app/Modules/<Module>/` — domain code. `app/Modules/Core/` — tenancy, audit, base classes, logging, exceptions, **the response security headers and the Sentry scrubber** (Phase 20).
- **Phase 20 (Observability & security hardening) is complete** — read **ADR 0017** before touching
  anything in `config/security.php`, `config/observability.php`, `config/sentry.php`,
  `config/pulse.php` or `app/Modules/Core/{Observability,Support/Security}`, and
  **`docs/runbooks/observability.md`** when something is broken in production. Five things about it
  are easy to get wrong. `SecurityHeaders` is **global** middleware, not a group — the headers
  belong to the response, and a group is how the one route nobody thought about becomes the one
  route without a header. The **CSP is nonce-based with no `unsafe-inline`**, which is only
  affordable because this app has no third-party script: a new inline tag needs the nonce
  (`Vite::cspNonce()`), and a new third-party host goes in `SECURITY_CSP_EXTRA_*` rather than into a
  loosened directive — and it is deliberately **not** emitted under `npm run dev`, so test a policy
  change against a built environment. Sentry's **scrubber is aimed at our own code**: the realistic
  leak is a log context becoming a breadcrumb, so log IDs, never prose or payloads, and add a key to
  `observability.sentry.scrub` rather than trusting the vendor's defaults. **A new expected refusal
  belongs in `sentry.ignore_exceptions`** with a comment, because that list is also the list of
  things we have decided not to be told about — but never the base `DomainException`. And `/pulse`
  is behind the admin panel's own four controls plus `AdminAbility::ManageOperations`: it is a
  cross-tenant surface, not a lesser one, and **Pulse is a clock while `/admin` is a tenant** —
  neither answers the other's question.
- `docs/` — knowledge base: `architecture.md`, `modules/<module>.md` (read before working a module), `decisions/` (ADRs), `runbooks/`, `compliance.md`, `ai-prompts.md`, `brand/brand-tokens.md`.
- `mvp.md` — phased plan + status table. **Phases 11 (Outreach), 12 (Notifications), 13 (Reporting & Analytics), 14 (AI Insights), 15 (Compliance & Privacy), 16 (Billing & Plans) and 17 (API v1 hardening) are complete** — read `docs/modules/outreach.md`, `docs/modules/notifications.md`, `docs/modules/reporting-analytics.md`, `docs/modules/ai-insights.md`, `docs/modules/compliance-privacy.md` and `docs/modules/billing-plans.md` before touching any of them. Compliance in particular: it reaches other modules through **three contracts, not by them knowing about it** — `LeadSourcing\Contracts\LeadInterestGate` (no recorded lawful basis, no discovery), `Outreach\Contracts\LeadRestrictionResolver` (how a prospect may be approached) and `Signals\Services\SignalsPersonalDataExporter`. Add a compliance rule by binding one of those, not by importing `App\Modules\Compliance` into another module. The do-not-contact table stays `outreach_suppressions`. Billing works the same way and is the **last** provider registered: it binds the real `AiPlatform\Contracts\CreditSource`, `LeadSourcing\Contracts\LeadQuotaSource` and `Auth\Contracts\SeatLimitSource` over the permissive stubs those modules ship as defaults, so no module imports `App\Modules\Billing` — change a plan limit by changing `config/billing.php` or one of those bindings, never by teaching another module what a plan is. Enforcement lives in the **guards**, not in middleware, because a queued discovery job and a scheduled watch spend a team's allowance with no request behind them; it can be switched off wholesale with **`BILLING_ENFORCE_PLANS=false`**, which makes the provider install neither the plan capability gate nor the three sources so each module's own permissive default stands (suspension, operator overrides and the AI cost allowance all keep biting), and **`BILLING_STRIPE_ENABLED=false`** separately stops every Stripe call without touching anybody's entitlement — the two are different questions and neither implies the other; and `usage_meters` is a **record** over the `ai_requests`/`discovery_runs` ledgers, not a counter the app increments. Reporting in particular: every figure is scoped by one window whose **cohort rule** is written down there, and its bounds must reach a query in **UTC** (`DateRange::constrain()`) or a non-UTC team's dashboard silently shifts. `signals-plan.md` — the Signals (trigger-event prospecting) build plan, phases S0–S6, **complete** (companion to `mvp.md`; see `docs/modules/signals.md`, `docs/runbooks/signals-demo.md` + ADR 0011). `lead-sources-plan.md` — the **free lead sources expansion** plan, phases L0–L14; **L0 is complete** (the licence/ToS spike + ADR 0025). Read its findings — `docs/modules/lead-sourcing.md` → _Free sources — spike findings (L0)_ — before building any source in it, and note three things: that plan's "ADR 0018" means **0025**, **L4, L8 and L10 are dropped** on the sources' own terms, and **L6 is superseded** by ADR 0023. `signals-v2-plan.md` — the Signals v2 plan, phases **S7–S16**, **all complete** (signal types are data a team owns — ADR 0018; the geography is plural and the outreach restriction follows the signal's own jurisdiction — ADR 0019; the builder drafts a type from a sentence and previews it before saving — ADR 0020; a watch can be pointed at the team's own accounts instead of a place — ADR 0021; one event is one card, and an article's identity survives a redirector; the feed is ranked, every card explains itself and the team's dismissals propose the next tuning — ADR 0022; a signal source is a registry entry and a type says which sources it runs on — ADR 0023, and S13b finished the set: the public record, a feed a team chooses, and a customer's own events; a signal arriving is now something a team can automate against, and an automation drafts an approach but never sends one — ADR 0024; S15 made the round-up name the news, gave every type its own cost and the library a curator; and **S16 made all of it safe to sell**). **After S9 the original ask is delivered**; everything after it is the moat. Eighteen things about Signals that are easy to get wrong after S16: a signal **type** is a row and not an enum (`SignalDefinition`; the four status/cadence/reason enums stay enums, and ADR 0018 §1 is the test for which is which), and `signal_definitions` is the one table holding both tenant rows and **platform presets** — only `PlatformPresetReader` may read a preset, a team **clones** one rather than referencing it, and nobody edits one. The query builder no longer reads `config('signals.templates')`: that key is seed data for the presets. Third, **where a watch searches and which law applies to its leads are two different questions** — `SearchRegion` answers the first, `Market` the second, and ADR 0019 is why `Market` must not grow to cover a region nobody has taken a legal position on. Fourth, the restriction on a converted lead **follows the subject**: the signal's own `resolved_market` first, the watch's `market` as a backstop, its regions able only to add, and an unresolvable place failing _toward_ the restriction — keying it on the watch alone was a permissive compliance bug (`docs/compliance.md` §3.11). Fifth, the composer **never saves** and the preview **persists nothing** — a draft is a suggestion the member commits, and a preview writes only its `signal_previews` ledger row, which is what makes the team's daily preview budget enforceable. Sixth, **a preset's templates are never shipped unspiked**: every one in the library has been run against live Serper `/news` and recorded in the module doc's spike tables, because a preset nobody ran is a guess with a label on it — eight of S9's 66 returned zero, and S10's spike contradicted its own plan (**every quoted query returned zero, 12/12**, and adding a keyword to a company name _lost_ results), which is why an entity query is a **bare name**. Seventh, a watch is **either** topical **or** entity-scoped — `signal_watches.signal_watchlist_id` decides, a spec carries places or entities and never both, and a long watchlist is a **ring** read through `entity_cursor` — a window filled by what one run can **afford** (one query per entity per region), advanced by the entities actually searched, rather than a list trimmed to its first forty forever. Eighth, `signals.matched_lead_id` ("the lead this is **about**") is not `signals.lead_id` ("the lead this was **converted into**"); the match is written as the row is built, with the lead's timeline entry **inside the same transaction**, and "Add to {Lead}" is `ConvertSignalToLeadAction` with a named target rather than a second Action. There are exactly **two** match confidences and a weak guess is **no match** — and the one company-name rule lives in `LeadSourcing\Support\CompanyNameKey` (`for()` strict, `bare()` **legal forms only**: do not put `holdings` or `group` back in that list, which is how "Acme" came to match "Acme Holdings Ltd"). Ninth, `SignalScope` is a **scope, not a status** — it crosses the status tabs rather than extending them, and the tab counts are scoped with it. Tenth, **a signal is one article and a `SignalCluster` is one event**, and the feed lists and counts the cluster's `primary_signal_id`: a member never actions a member row, so dismiss, restore and convert are propagated across the cluster while `lead_id` deliberately is not (exactly one article is a lead's provenance). `SignalClusterer` holds **two** questions — a provisional headline overlap _before_ the AI (which is where the one-classification-per-story saving comes from, and which `signals.cluster_before_ai=false` turns off safely) and the real `(event_key, subject fingerprint, ISO week)` key _after_ it (which is what consolidates the cards either way). So the savings depend on the similarity numbers and the correctness does not; the fingerprint is a **company** name and never a person's, because a cluster has no retention window of its own. Eleventh, **`signals.dedupe_hash` is an article's identity and `url_hash` is only its link**: for a host on `signals.redirect_hosts` the identity is the content hash (`sha1(source name + normalised headline)`), because a Google redirect's token cannot be unwrapped and a varying one re-admitted the same article on every run. The unique index moved with it, the ignore list matches an **outlet's name** as well as a host for the same reason, and `SignalRejectionLedger` remembers a "no" for 30 days keyed by the article _and_ the set of types that were offered — never for a key the run did not offer, because that is a statement about our prompt rather than about the article. Twelfth, **`signals.heat` is nullable and an unjudged component is left out of _both_ sides of the average** — `null` is “not scored”, not “scored zero”, or the number would measure how much Alima knows about an event instead of how much the event is worth, and `SignalSortOrder` orders nulls last explicitly because MySQL and SQLite disagree. `signals.score_breakdown` is **stored and read back, never recomputed**, because the card must explain the score the feed was actually ordered by; its figures are literal and only Alima's own sentences carry `evidence_translatable`. `SignalTuningAdvisor` **proposes and never applies** — accepting is an ordinary audited edit, a decline is kept so it is never raised twice, and “raise this floor” may never lower one. The full-article fetch is **off by default**, reuses `Core\Contracts\WebContentFetcher` and the existing `signals.extract_event` prompt, honours `robots.txt` via `Core\Support\RobotsPolicy`, and **stores no body** — only `article_fetched_at`; it runs **after** the run's commit, so nothing in it may escape (ADR 0022). Thirteenth, **a signal source is an enum and a signal type is a row, and that is not a contradiction** — ADR 0018 §1's test still decides it: a class exists per source, so the application branches on one and not on the other. `SignalSourceKind::isAvailable()` separates a case that is wired up from one only declared (`companies_house`, `feed` and `webhook` are declared), and a definition cannot be saved against an unavailable one. Add a source by registering a `SignalSourceProvider` in `SignalsServiceProvider`, never by branching in the run; give it its **own** breaker key under `signals:cb` and a matching `Admin\Enums\PlatformProvider` case, or an open breaker is invisible to operations. `signal_definitions.source_keys` is **read through `sourceKinds()`**, which falls back to news for a null, an empty list or a key this build does not know — a type that searched nowhere would complete a run successfully having found nothing. And the one to hold on to: **a provider's health and a query's validity are different questions.** A 400 or 422 **whose body matches `signals.serper.query_rejection_markers`** is a verdict about _that query_ (Serper refuses `site:` and quoted templates on this account tier), so it raises the non-retryable `SourceQueryRejected`, leaves the breaker shut, is caught **per query** by a typed `catch` and is counted under `rejected` on `signal_runs.source_breakdown` while the rest of the plan proceeds — treating it as an outage made one team's bad template fail and re-bill their whole run three times over. **Any other 400 fails the run loudly**, because the same status is how an exhausted account and a parameter we send wrongly arrive, and swallowing those per query would complete every run green with nothing found, for ever; and a source that refused **every** query fails the run too, because “some refused” is about a template and “all refused” is about something systemic (ADR 0023 §4). Fourteenth, **a source is addressed in one of three ways, and mixing them up is a cost bug in the expensive direction** (S13b): a _query-based_ source (`isQueryBased()` — news, web search) takes a string and multiplies out by place × region × template; a _subject-addressed_ one (`addressesSubject()` — Companies House) takes a company number, so one query per account and no multiplication, which is also why it runs on a **watchlist watch only** — there is no cross-company filings endpoint, and the topical half of its task was dropped on evidence (2,422 new London software companies a month for one SIC code); and a _definition-addressed_ one (a feed, the webhook) takes what is on the definition, so one query each — a feed asked per place per region per template would be fetched forty times a run for one identical document. Three more S13b rules worth holding. A **registry filing carries its own classification and skips the AI batch** (`SourceItem::$classification`, `ExtractedSignal::structured()`), because `description_values` is the registry’s own extraction — but it still passes `resolveDefinition()` and the definition’s floors, since a source asserts a confidence and not that the team wants the event; only code **we** wrote against an authoritative provider may populate that field, never the webhook. A **watchlist name is resolved to a company number once and remembered**, from `leads.company_number` for free where the team’s own data knows and otherwise from a search that accepts **only an exact `CompanyNameKey::for()` match** (never `bare()`) — a filing arrives with confidence 100, so nothing downstream would doubt a wrong company; `company_number_checked_at` is the negative cache, and a _transport_ failure must leave it unstamped. And a **pushed event is stored, then read back like any other source**: `POST /api/v1/signal-events` accepts into `signal_inbound_events` and `WebhookSignalSource` offers it to the next run, which is what makes “the customer supplies an observation, Alima decides what it means” true rather than aspirational — and what keeps a retry loop from triggering an AI call. Its secret is **encrypted, not hashed** (verifying an HMAC means recomputing it), shown once, one per type; its window must stay **below** the 30-day rejection memory, because there is deliberately no `processed_at`. The SSRF guard for the one source whose address a customer supplies is `Core\Support\Security\SafeUrl`, **shared** with `HttpWebContentFetcher` and never copied; it now hands back the addresses it approved so the feed can **pin** them, and a feed whose host does not resolve is refused rather than attempted. And the S13b review added the **fifteenth**, which is ADR 0023 §4a: **a 4xx has three meanings, not two** — a breaker answers _is the provider up_, `SourceQueryRejected` answers _was that a sensible thing to ask_, and `SourceAddressNotFound` answers _is the thing we addressed there at all_. The third exists because the first two are both questions about **us**, which was exhaustive only while every source was addressed by a string we composed: as a provider failure one struck-off `leads.company_number` failed a whole watch on every run for ever (the entity cursor only advances on completion), and as a query rejection a moved feed failed a run too, because a feed is asked **one** query so "some refused" and "all refused" are the same event. A skip is caught per query, counted under `skipped` on the breakdown, and excluded from the all-refused rule. Three more things that review settled and that generalise past Signals: a **cache key is a tenancy decision** (the feed's poll floor and ETag were keyed by URL alone, so one team's poll of a public newsletter silently blinded every other team — a denial, not a leak, which is the half nobody tests for, and a preview must hold none of a run's state); a **capped window must exclude what it has already done** before the cap is spent (`signal_inbound_events.dedupe_hash` exists so the exclusion can be a `whereNotExists` rather than a filter after the fact, because `sha1()` is not a function SQLite and MySQL agree about); and **`! isQueryBased()` is not "addresses a subject"** — that conflation put a feed query behind every template and a phantom registry query behind every entity, so ask the enum the question you mean (`addressesSubject()`, `carriesAFetchableArticle()`). And the **sixteenth**, which is S14: **a playbook prepares an approach and can never send one** (ADR 0024, `docs/compliance.md` §3.12). `Signals\Contracts\SignalOutreachDrafter` is declared in Signals with a **refusing** default and bound by Outreach — the one seam in the codebase whose default refuses rather than allows, because the question is whether a prospect may be approached and a permissive default would be Signals settling a compliance question Outreach exists to settle — and it has `channels()`, `tones()` and `draftForReview()` and **no `send`**, which a test over its method list keeps true. A step handler calls the **owning module's Action** and never reimplements one (and the two that set a whole set — assignees, tags — are used **additively**, or a rule would take a lead off the person working it); a notify step **records an intent** and the job aggregates it, because a rule matching twelve signals must be one message; the evaluator is **pure over nine scalars** so the preview and the dry run are predictions rather than guesses, with an empty condition list meaning _do not care_ and **unknown not zero**; a cluster member matches nothing; the preview **spends nothing** and so has a window rather than a budget, and a read-only member may run it; an unattended rule acts as the creator or the owner and **refuses rather than running as nobody**; and the log **outlives the rule** (`nullOnDelete`, name copied) while dying with the **signal** (`cascadeOnDelete`, so the retention sweep takes it). And the **seventeenth**, which is S15: **a type's cost is two figures and they go in two columns** — `signal_definition_spend.search_cost_micros` is **measured** (a query names exactly one type) and `.ai_cost_micros` is **allocated** by share of results (one classification call serves every type on the watch, which is S11's saving), so one total would show an allocation as a measurement; the allocation's parts must sum to the whole, the row is keyed by `event_key` so a deleted type keeps its history, and it is a **record** written once per completed run with `insertOrIgnore` + `incrementEach` rather than a driver-specific upsert. `costPerConvertedMicros()` is **null, not zero**, when nothing converted — a zero reads as “free”. ## 4. How to work a phase (ADR + §8 of the kickoff)

1. Read this file, the phase in `mvp.md`, and the relevant `docs/modules/*.md`.
2. Plan briefly, then implement in **small commits** with **conventional commit messages**.
3. Write/update tests alongside the code.
4. Run `composer lint`, `composer analyse`, `composer test`, and the frontend build; fix everything.
5. Update the module doc(s) (Code map, Data model, Key flows, **Changelog row**), `docs/architecture.md` if structure changed, `CHANGELOG.md`, and tick tasks + the status table in `mvp.md`.
6. Summarise what was done, anything deferred, and anything the user must do (keys, accounts, decisions).

**Before working on a module:** read its `docs/modules/<module>.md`. **After finishing:** update that doc and append a Changelog row. New module → create its doc from `docs/modules/_TEMPLATE.md` and add it to `architecture.md` + this file.

**four figures, four questions** — fit from `lead_scores`, readiness, timing and confidence — so `fit_score` is _not_ copied onto `leads`; `max` rather than a sum or an average, corroboration counted by **distinct sources**, only a trigger event feeds timing, `reliability` stored at capture and never looked up again, and **null is not zero** so an unjudged lead is never hidden; a dispute is one member's and its effect is the team's, only `wrong` moves a number, and a disputed item is **dropped** rather than weighted zero; the why-now sentence may use the supplied evidence and nothing else and **never appears without it**; every lead gets its provenance from a model observer so the guarantee survives the next creation path; and the suppression is gated on the Pennant flag **inside `LeadQueryBuilder`**, because a list that honoured the column without asking the flag is how a dark launch stops being dark) · 0029 **contact data and the enrichment contracts** (PL2: four **narrow** capability contracts behind `EnrichmentProviderRegistry` — the third instance of ADR 0008/0023's pattern — with the **order in config** rather than in registration order, and a provider refused at registration if it claims a capability whose contract it does not implement; **a miss is a result and a failure is an exception**, with three named failure causes because they are three different decisions; one enum for what is known about an address however it was learned, which is why widening it fixed four `=== MxFound` comparisons that would have scored a _verified_ address below a routable one — a literal compare against "the best value that exists" is a bug waiting for the enum to grow; **masking follows who was paid**, not whether a value exists, so a page-scraped address and a company switchboard are never masked and the resource sends one already-masked field per value; `Core\Support\ContactIdentity` is the one definition of an identity and `SuppressionType` delegates to it, because two tables hashing differently is not a missed index but an email to somebody who opted out; and **one** experimental adapter ships because only one vendor's response shape could be confirmed from its own docs — a reference adapter built on a guess is worse than none, since it looks finished) · 0030 **the enrichment waterfall** (PL3: `enrichment_attempts` is **append-only and is the money** — every paid call with its cost, hit or miss, because the commercially interesting questions are all about the misses, and everything downstream reads the attempts rather than the run's summary; **three kinds of nothing** — a miss, an error and a skip — kept apart so an outage does not look like a bad vendor and a hit rate does not quietly include the days it was down; **stop at the first _good-enough_ answer**, which is why `accept_all` is not the default stop; never ask an unanswerable question and never sleep on a rate limit; the **reservation lives in the job, not the request**, is released in a `finally`, and commits what the **attempts** say was spent; a **refusal is not a failure**, and a capability refusal leaves no run while a spent allowance does; a broadcast carries **counts, never values**, because it reaches every member with a screen open; E.164 is libphonenumber's job and a refusal is a valid answer, since a wrong normalisation produces a valid number belonging to somebody else; and `AttemptRecorder` swallows its own failures on purpose — the row is written after the money left) · 0031 **the usage ledger, plan gating for contact data, and top-ups** (PL4: `usage_ledger` is Billing's own fourth ledger because a contact reveal is the first chargeable act with **no table behind it** — same shape as the three it joins, append-only and read by aggregate, so ADR 0012's “never increment a counter at the point of use” still holds; the plan's `team_allowances` projection was **not** built because `used`, `reserved`, `topped_up` and `included` are all derivable and a second table is a second answer, and what a reserve really needs — a mutex — already existed as the `usage_meters` row for `(team, metric, period)`, which the reserve locks and then **recounts inside**, since the lock alone would serialise two requests that both read “one left”; a hold is settled by **writing beside it** and settling is idempotent on the handle, because the failure that happens is a worker dying between its last provider call and its commit; an **absent allowance means zero** for the six new metrics and **unlimited** for the three old ones, which is `StubSignalQuotaSource`'s argument again and also why there is no unlimited contacts plan at all; `CreditReserver` is the fifth seam and the **first bound whatever `BILLING_ENFORCE_PLANS` says**, because a reveal is money leaving the building per unit and so the reserve path is a cost guard rather than a plan feature; a contact metric **never meters** — a metered reveal is an uncapped vendor bill — so the answer is a **top-up** bought before the spend, three metrics only, lapsing with its period, with the client naming an **option index** and never a Stripe price and **nothing granted until the paid webhook**, idempotent on the Stripe **event** id; that listener is on **`WebhookReceived`**, because Cashier fires `WebhookHandled` only for the event types it handles itself and `checkout.session.completed` is not one — a listener on the other event would have granted nothing, silently, for ever; `MarginGuard` refuses **phone reveals only** above `max_vendor_cost_ratio`, exempts a team with no price, and checks **before** the hold; `enrichment_attempts` joined the platform cost rollup, which is ADR 0016's own risk note arriving; and three things the plan asked for needed no code at all — rollover, because an allowance is derived per period, the low-balance notices, because `UsageAlerter` is generic over the summary, and `can-*` gates, because `remaining()` is the one answer) · 0032 **the compliance core** (PL5: `outreach_suppressions` stays the one do-not-contact table and gains one type, whose normaliser requires a digit because a pasted CSV header would otherwise become a permanent entry; one gate on every path that stores or sells a contact, asserted by a test over the **seam** rather than per screen, because a path that forgets to ask would pass a behaviour test it never wrote; a screening is a **fact to record and not a reason to refuse**, so it is a second seam that runs after the charge and swallows its own failures; **unknown is not clear** in four states and three of them are not a pass, which is why no licensed TPS adapter shipping is safe; the PECR subscriber type is **derived, flat across the seam, null outside the UK, and warns rather than blocking**; and the public door **verifies before it acts** -- a platform table with no `team_id`, a signed link that is the only authentication there can be, the suppression written before the deletion, a cross-tenant purge that reuses the per-team erasure, and an operator queue that can close a request but cannot decide whether to honour one)

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:

- When graphify-out/graph.json exists, run `graphify query "<question>"` before your first grep, search or source-file read for a codebase question, and put this rule in every subagent prompt that explores code. Read raw files only for lines the graph or an earlier read already located. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
- A committed graphify-out/graph.json is rewritten whole on every build, so a large diff to it in a pull request is expected. Do not flag it as churn or suggest skipping the graph rebuild or its hooks.
