## Found while building, not fixed

- **`invoice.payment_failed` has never reached the app** (found in PL4). `Billing\Listeners\SyncSubscriptionFromStripe`
  listens on Cashier's `WebhookHandled`, which Cashier fires **only** for the event types it has a
  handler method for — and it has no `handleInvoicePaymentFailed`. So the "your card was declined"
  notification to Owners and Admins, added in Phase 19b, has never fired; Stripe's own dunning email
  is still the only signal. The fix is a **second** listener on `WebhookReceived` (PL4's
  `GrantTopUpFromStripe` is the pattern), not a change to this one — moving it would make it run
  before Cashier has synced the subscription row it re-reads. One small listener plus a test; PL12
  unless it comes up sooner.

- **A public request's phone number is not honoured automatically** (PL5, by decision — ADR 0032 section 6).
  The verification click authenticates a mailbox and nothing else, so suppressing and erasing on a
  number anybody could have typed into the form would let somebody have a stranger's — or a
  competitor's switchboard — blocked across every tenant. The number is stored on the request and
  shown in `/admin/subject-requests` for an operator to act on. Honouring it automatically needs the
  number verified too: an SMS code, a provider, a cost, and a section 5 question about whether we may
  send one to a number we were given by somebody who may not own it.

- **Nothing in the product reads a `company_number` suppression** (found in PL6). PL5 added
  `SuppressionType::CompanyNumber` and a bulk load for it, and a team can fill their list with
  registration numbers — but no check consults that type: not `OutreachGuard`, not
  `SuppressionApprovalGate`, and so not the export either. A team loading company numbers today gets
  a list that looks honoured and is not. The fix is one query in `SuppressionList` plus a question on
  whichever seams should ask it, and it has to be the same answer for a send, a sync and a file,
  which is why PL6 did not fix it only for the file. **PL7 did not fix it either, for the same
  reason** — the CRM push asks `allowsDomain()` and so has the same blind spot as the export. PL12.

- **A webhook endpoint has no volume ceiling of its own** (PL7, by decision — ADR 0034). `lead.created`
  fires once per company and a discovery run finds hundreds, so a team that ticks it has signed up to
  a delivery per lead: the enum flags it as high-volume on the screen, the endpoint lookup is memoised
  per process and the payload is built behind a closure, so a team with **no** endpoints costs one
  query per run. What is not there is a cap, because the volume follows directly from what somebody
  ticked and a cap would silently stop an automation they depend on. Revisit if a customer's receiver
  is ever why our own queue backs up — the figure to watch is `webhook_deliveries` growth against
  `webhooks.retain_days`.

- **`synced_hash` is over the fields we believe a connector sends** (PL7, noted in the code). It is a
  fixed list of lead columns plus the why-now line, not a hash of the connector's actual request, so a
  connector that mapped a field the list does not name would not re-push when that field changed. It
  is correct for PL8 and PL9 as specified; it needs revisiting the day a connector's field mapping
  becomes configurable per team.

- **A plan's `export_rows` figure was written thinking in leads** (PL6). The CRM-ready preset
  writes a row per contact, so a team exporting 400 leads with three contacts each spends 1,200
  rows rather than 400. That is correct — it is 1,200 rows — but the figures in
  `config/billing.php` were chosen before a per-contact preset existed, and they want a look before
  launch. No code change; a number per plan.

- **`tests/Feature/Icp/ComposeIcpTest.php` has two failing tests, and they predate PL5** (confirmed by
  running them against a clean tree). Both assert on `session('inertia.flash_data.draft.*')` after
  `icp.compose`, and both fail at the first `expect`. Nothing in PL5 touches the ICP composer; it is
  listed here so the next phase does not inherit it as a mystery. `composer test` is otherwise green
  at 3,082 of 3,089 with 5 skipped (re-confirmed after PL7).

- **Arabic copy for PL5's 45 new strings needs brand-owner sign-off** (`brand-tokens.md` §7), the same
  caveat PL4's 26 carried. They are in `lang/ar.json` as a translator's starting point, and the public
  privacy-request form is the first unauthenticated screen where that matters: a person reading it has
  no account, so there is no language preference to fall back on but the browser's.
