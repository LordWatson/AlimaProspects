# Admin (internal operations panel)

> Status: **MVP — complete (Phases 19a, 19b and 19c)** · Last updated: 2026-11-01 · See **ADR 0014** (supersedes ADR 0009), **ADR 0015** and **ADR 0016**

## Purpose

The panel the AlimaProspects team uses to operate the platform. It reads and writes **every** resource in the product from **outside team scope**, lets an operator fix a customer's record, suspend a tenant, perform account operations and impersonate a user — with every cross-tenant read and write audited. It also holds **the business's own numbers** (MRR, churn, the onboarding funnel and gross margin per tenant) and the operational views that make the platform runnable without a shell: failed jobs, queue and schedule health, provider health, the cross-tenant audit trail, compliance activity, signal runs and outreach deliverability.

It explicitly does **not** own any business rule. Where a module owns an operation, the panel calls that module's Action; the generic writer is only for records nobody wrote an Action for. It is also **not** a place a tenant ever reaches: `/admin` answers 404 to everybody who is not an operator.

Three things about it are decisions rather than omissions, and all three are stated here so nobody has to infer them:

- **Web only.** There is no `/api/v1/admin`. A token that can read every tenant is a liability no MVP ops task needs, and it would have to be scoped, versioned and specified like everything else in ADR 0013. The module ships no `routes/api.php` at all, and `AdminRouteContractTest` asserts the API surface stays empty.
- **English only.** An internal tool carries no EN/AR or RTL obligation (ADR 0007 is about the product). The tenant app and the mobile app remain bilingual; admin screens use plain strings and no `t()`.
- **Not Filament.** ADR 0014 has the four reasons. The first is that Filament's generated screens write straight to models, which is the second unvalidated write path CLAUDE.md §2's rules exist to prevent.

**Phase 19c** adds exactly one table, and widens nothing:

| Table                    | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `platform_daily_metrics` | `(date, metric, dimension) → value`, unique on the three. A **record over the ledgers**, not a counter (ADR 0012's rule for `usage_meters`, applied again): recomputable, backfillable, and nothing in the application increments it. `dimension` is `''` rather than null for the undimensioned total, because MySQL treats NULLs in a unique index as distinct and a duplicate here is a figure silently doubled. `value` is **signed**, because MRR contraction and churn are negative by definition. |

Plus seven date-only indexes (`ai_requests`, `discovery_runs`, `signal_runs`, `contact_attempts`, `outreach_messages.sent_at`, `leads`, `audit_logs`). Every one of those tables is already indexed on `['team_id', <timestamp>]`, which is right for every tenant-facing query and **useless** to the rollup: a composite index is only usable from its leading column, and the rollup is the one reader with no team to narrow by.

## Key flows

### Crossing the tenancy boundary — the one to understand first

`BelongsToTeam`'s global scope is a **no-op when no team is active**. So the panel's cross-tenant reads work by _removing_ a constraint, not by adding one: `PlatformContext` clears `TeamContext`, and every tenant model is immediately unscoped.

That is exactly what an admin index needs and exactly what must never happen anywhere else, so two guards sit around it:

1. `PlatformContext` **refuses to run on a route that is not named `admin.*`** (a 500 with an explanation). Applied by accident to the leads list, it would silently serve every tenant's prospects to whoever asked.
2. `AdminRouteContractTest` asserts from the other direction: **no route outside `admin.*` may carry it**, and every route inside `admin.*` carries the whole stack and exactly one known ability. A per-route test only covers the routes somebody remembered to write one for.

Reading **one** tenant does not get a second query path. `TeamOperationsController` uses `TeamContext::run($team, …)`, so a per-team figure comes back through the same global scope and the same policies the tenant's own dashboard uses. A hand-written `where team_id` would be a second implementation of tenancy, and the day the two disagreed the panel would be the one that was wrong.

### Auditing — including reads

`AuditLog` conventionally records writes. An operator opening a tenant's prospect list is a **privacy event** — somebody outside that business read their customers' details — so it leaves a row too:

| Action                                                  | When                                                                         |
| ------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `admin.resource.viewed`                                 | An index, with the resource, filters and a count                             |
| `admin.record.viewed`                                   | One record, or an edit screen                                                |
| `admin.record.created` / `.updated` / `.deleted`        | A generic write                                                              |
| `admin.team.suspended` / `.restored`                    | A suspension applied or lifted                                               |
| `admin.user.*`                                          | Password reset sent, 2FA cleared, sessions or tokens revoked, email verified |
| `admin.impersonation.started` / `.stopped` / `.expired` | An impersonated session                                                      |

Two properties hold throughout, and both are tested:

- **Entries carry ids and counts, never rows — and never the search term.** A log of who looked at personal data must not itself be a copy of it. An update records the _names_ of the fields that changed, not the values; an index records `searched: true` rather than what was typed, because operators search by email address and by name, and `audit_logs` is append-only and outside Compliance's retention sweep. If somebody has to reproduce exactly what an operator saw, the URL is in the ticket.
- **Entries are stamped with the _target_ tenant.** This is the subtle one. `AuditLogger` reads `team_id` from `TeamContext`, which the panel has deliberately cleared — so `AdminAudit` passes the target team explicitly and writes inside `TeamContext::run()`. Without it, every admin entry would land with `team_id = null`: the row exists, nothing errors, and the per-tenant audit view — the one a customer's support ticket is answered from — shows nothing at all.

### The resource registry

One declarative `Admin\Resources\<Name>Resource` per model, listed in `config/admin.php`, rendered by three generic Inertia pages. A descriptor declares columns (reusing Reporting's `ColumnFormat`), detail-only columns, editable fields with their validation rules, searchable columns, filters, sorts, eager loads, and which of create/update/delete it permits.

Three rules keep it in shape, each enforced by a test rather than by intention:

1. **Descriptors return data.** Anything that needs to _decide_ something gets a bespoke screen. `TeamOperationsController` and `UserOperationsController` are what that looks like. A descriptor growing a conditional is the failure mode to watch for.
2. **Where a module owns the operation, the panel calls its Action.** Member removal → `RemoveTeamMemberAction`. Role change → `UpdateTeamMemberRoleAction`. (Phase 19b: plan change → `SwapPlanAction`.) The generic writer is for the rest.
3. **Everything is off by default.** `allowsCreate`, `allowsUpdate` and `allowsDelete` all return false on the base class.

Where the registry stands today:

- **Create** is permitted on exactly two resources — `icps` and `outreach-templates` — and the rule is narrow: only where **every column the table requires is a field the descriptor declares**. `lead-tags` fails that test (`slug` is derived from the name by `LeadTag::normalise()`, and deriving a column is logic), so create stays off there and the workspace's own first-use flow is the way in.
- **Delete** is permitted on exactly three — `lead-tags`, `saved-views`, `push-devices` — each a row whose only dependents cascade, and each with a real support reason. `AdminRouteContractTest` pins that list, so changing it is a failing test and a conversation rather than a quiet diff.
- **Everything else is read-only**, and the descriptors say why individually. The ones worth knowing: `outreach_suppressions` (an erasure or opt-out entry cannot be lifted — a generic delete would be a way to un-opt-out somebody), `audit_logs` (an audit trail an operator can edit records only what somebody was willing to leave behind), `ai_requests` (a team's allowance, usage meter and margin are computed from it), `lia_records` (somebody else's legal paperwork), `lead_contacts` (erasure goes through Compliance, which also suppresses the identity so the next discovery run does not re-source the person who asked to be forgotten).

The cross-tenant index over `leads` is the **only query in this product with no `team_id` in its `where` clause**, which makes `ResourceQuery` both the privacy and the performance risk. Sorts and filters are whitelisted against the descriptor, searches bind the term rather than building SQL, pagination has no "all" escape hatch, and relations are eager loaded (a dotted column without its relation declared fails the contract test, because `preventLazyLoading` would turn it into an exception).

### Suspension

`teams.suspended_at` + a required reason. What stops is **sourcing, sending and spending**; what does not stop is signing in and reading. Locking people out of data they own is the wrong lever — it punishes the colleague who did nothing — and a tenant who cannot reach their own data cannot exercise their rights over it either.

Enforced in the **guards, not in middleware**, which is ADR 0012's argument unchanged: a queued discovery job and a scheduled signal watch spend a team's allowance with no request behind them. Admin registers last in `bootstrap/providers.php` and **decorates** three bindings with `extend()`:

| Guard                                    | Decorator                        | Effect when suspended                               |
| ---------------------------------------- | -------------------------------- | --------------------------------------------------- |
| `AiPlatform\Contracts\CreditSource`      | `SuspensionAwareCreditSource`    | Allowance limit 0, usage preserved                  |
| `LeadSourcing\Contracts\LeadQuotaSource` | `SuspensionAwareLeadQuotaSource` | Quota limit 0 (not `null`, which means _unlimited_) |
| `Outreach\Contracts\TeamSendingGate`     | `SuspensionAwareTeamSendingGate` | Every sendable channel blocked with `TeamSuspended` |

`extend` rather than `bind` is the point: a bind would **replace** Billing's plan-backed source, and Admin has no business knowing what a plan is. Add a rule, do not take over.

`TeamSendingGate` is a **new seam Outreach ships** (with a permissive default, like Auth's `UnlimitedSeatLimit`), not a reuse of `LeadRestrictionResolver`. Binding over the restriction resolver would have been the shortcut, and it would have told a member that _this prospect_ may not be approached — a false statement about somebody else's legal position, recorded in the team's compliance history as though it were true. `OutreachBlockReason::TeamSuspended` is configuration rather than compliance, and its guidance says to talk to us, because it is the one refusal the team cannot fix themselves.

### Impersonation

Start is an admin route behind `admin.can:impersonate` (`super_admin` and `support` only — never `finance`, never `read_only`). **Stop is not**, and is named `impersonation.stop` rather than `admin.impersonation.stop`: by the time an operator wants out, `Auth::user()` is the customer, so an admin-gated stop route would 404 the only way back and leave them inside somebody else's session until the TTL expired. Its authorisation is the session itself.

What it is not allowed to be:

- **Not a way to act on a customer's behalf.** `config('admin.impersonation.blocked_routes')` is one list, in one file, of route-name patterns: outreach sending, every billing write, erasure and export, CSV exports, passwords, email, 2FA, passkeys, API tokens, and the team and account themselves. `RestrictImpersonatedSession` enforces it on the whole `web` and `api` surface. A per-module annotation would have been eight places to forget, and "what can't an operator do inside somebody's account?" would be a question you answered by reading all of them.
- **Not a way to become another operator.** Refused outright: it would put their powers behind this session with their name on the trail.
- **Not something that outlasts the job.** `ADMIN_IMPERSONATION_TTL` (60 minutes), ended by sign-out, and `ShareImpersonation` expires it on the next request — by **handing the operator back to themselves**, not by signing out. `SessionGuard::logout()` cycles the _authenticated_ user's `remember_token`, and at that moment the authenticated user is the customer: the obvious implementation signs a real customer out of every device they ticked "remember me" on, because an operator left a tab open. `logout` is on the blocked list for the same reason — stop impersonating first.
- **Not a way to inherit the operator's own confirmations.** The session's data survives the login, so `start()` forgets `auth.password_confirmed_at`; otherwise an impersonated session would count as password-confirmed for anything behind `RequirePassword`.
- **Not silent.** Start and stop are audited against the tenant; the banner is in the app shell so it is on every tenant screen rather than on the screens somebody remembered; and `impersonated_by` rides in `Core\Support\AuditContext`, so **every write the session makes — through whichever module's Action, none of which know impersonation exists — records the operator behind the customer**. That ambient context is the one Core change this phase needed: there is no layer between an Action and `AuditLogger` to annotate from.

### Plan-driven capabilities — one question, four answers (19b, ADR 0015)

`Core\Contracts\CapabilityGate` has one method, and it is the **only** way anything in the product
asks whether a team may use a feature. Three bindings decorate it, in provider registration order:

| Layer            | Binds                    | Adds                                            |
| ---------------- | ------------------------ | ----------------------------------------------- |
| Core (first)     | `AllCapabilitiesEnabled` | the permissive default — everything on          |
| Billing          | `PlanCapabilityGate`     | the plan's own `capabilities` list              |
| Admin (**last**) | `GovernedCapabilityGate` | suspension, the kill switch, per-team overrides |

The order is the feature, and it is asserted layer by layer and in collision by `CapabilityGateTest`:

> **suspension → global kill switch → per-team override → plan → permissive default**

Two of those would be wrong reversed. **The kill switch beats a per-team override**, because an
operator reaching for it is dealing with something broken and hunting down every team-level exception
first is how an incident becomes an outage. **An override beats the plan in both directions**,
because "give this pilot a feature their plan excludes" and "switch this off for a customer whose own
compliance team asked" are both real requests.

A plan with **no `capabilities` key at all** falls through to the permissive default. A missing
configuration is not a product decision.

Enforcement is in the **guards**, not middleware — a queued discovery job and a scheduled watch spend
a team's allowance with no request behind them. `capability:` middleware is the courtesy half, so a
member who clicks a link their plan excludes gets a sentence (402) instead of a half-rendered page.
`Capability::enforcedAt()` names the real enforcement point for every case, and
`CapabilityEnforcementTest` **walks the enum and proves each one refuses** — a capability that is
declared but not enforced is worse than one that does not exist, because the pricing page promises a
gate that is not there. Writing that test found two false claims: nothing under `/api/v1` consulted
the gate at all (so the kill switch could not stop API traffic, and a token outlived the plan that
justified it), and the insights API had no capability check although the web screen did. Both are
closed — `capability:api_access` is on the whole api group, `capability:ai_insights` on the insights
API routes, and `IssueApiTokenAction` checks before issuing.

`CapabilityExplainer` is what stops four layers becoming a guessing game: for each capability it
reports the resolved answer, what the plan alone would say, and **which layer decided**. It asks the
gate for the answer rather than re-implementing the order — the precedence has exactly one
implementation, and it is not this one.

### A plan grant outranks Stripe (19b)

`PlanResolver` consults a grant **above** a subscription:

> **grant (inside its window) → live Stripe subscription → trial → default plan**

This is what makes "turn Stripe off" and "take somebody's plan away" two different acts. An invoiced
enterprise customer has no subscription and must not be on Free; a team whose subscription says
`canceled` because of an unprocessed webhook must not lose its contracted features. A grant carries
its own numbers, because a contract says 25 seats where the price list's Enterprise row says
unlimited — and `null` on a grant means "use the plan's number", not "unlimited". Granted teams get
their own `SubscriptionState::Granted`, because the billing screen has to say something different: no
card to change, no invoices, nothing to cancel.

One grant at a time, and **one live or pending grant**, not one in force: revoking only what is
currently in force left a future-dated grant untouched, so granting Scale today and Enterprise from
next month and then Team today stacked two unrevoked rows, and which one won next month became a
tiebreak rather than a decision. The team row is locked for the swap, so two operators granting at
once cannot each revoke what they saw and insert.

`teams.billing_mode` is a **separate axis** and grants nothing. Moving a team to invoiced billing
stops checkout and stops metering — reporting overage against a subscription Stripe is not billing is
how a command logs an error every morning — and leaves entitlement alone. Which means a team moved
off Stripe **without** a grant sits on the default plan, and if it was trialling it drops there
silently when the trial lapses. Both the provisioning dry run and the mode-change toast say so.

### The Stripe switch is a product state, not an outage (19b)

`StripeSwitch` is read in three places, and each answers in a way an operator would recognise: the
container binds `DisabledBillingGateway` over the real one, so a checkout attempt is a
`BillingException` with a sentence; the billing screen does not render a button that would throw; and
`SyncSubscriptionFromStripe` **returns without processing** a webhook that arrives anyway. The
middleware that 404s the webhook route is defence in depth — this is where "switched off" has to mean
something, because a misconfigured proxy or a route cached before the switch flipped must not quietly
change a team's entitlements while an operator believes Stripe is not being listened to. It returns
rather than throws: Cashier has already answered 200, so the honest move is to leave the event
unprocessed and let the operator re-sync.

### Platform settings — a schema, not a bag of strings (19b)

Every key `platform_settings` may hold is declared in `config/admin.php` with a type, rules, a
default and help text, and **both `get()` and `set()` throw on an undeclared key**. Every key is a
literal in our own code, so an undeclared one is always a typo — and a typo that returned null was
the worst available failure here: `bool('billing.stripe_enable')` reads as false, which switches
Stripe off, and looks exactly like a working screen.

The schema is what lets the settings screen be **generated** rather than hand-written, and what lets
a new kill switch be one config entry. A setting with an `allowed` list has its items validated
against it, so `signal` for `signals` is refused rather than saved as a kill switch that kills
nothing — which is a thing you find out during the incident you reached for it in.

**A trap found and fixed here:** a setting name _contains dots_, so a validation rule keyed
`settings.billing.stripe_enabled` is read by Laravel as three levels of nesting the payload does not
have. `data_get()` returns null, `sometimes` skips the rule, and **every rule on this form was a
no-op**. `UpdateSettingsRequest` now validates each setting under a dot-free alias and maps the
errors back to the dotted name the screen indexes by.

The screen writes through `UpdatePlatformSettingsAction`, which is **one transaction** for the whole
page — each key is still its own audit entry, but a failure on the third setting no longer leaves the
first two applied. The page also shows the pending changes in words and takes a second press before
switching anything off platform-wide.

### Provisioning a business (19b)

`ProvisionTeamAction` is the Action behind the screen a sales person uses after a call. It calls
Auth's own `CreateTeamAction` rather than writing the team itself, and that is a requirement rather
than a preference: a provisioned tenant has to be indistinguishable from one that signed up, so the
Owner membership, the `team.created` audit entry and the trial-starting model event are all the ones
a signup produces.

**An operator never chooses a customer's password**, and the way in is a **password-reset link, not a
team invitation**. The plan for this phase had it the other way round and the code refused:
`InviteTeamMemberAction` exists to invite somebody to a team they are _not_ in, and `CreateTeamAction`
has just made this person the Owner. Rather than write the invitation row by hand and bypass the seat
check and audit entry that belong with it, provisioning calls 19a's own `SendUserPasswordResetAction`
after commit — so a provisioned account's first credential leaves the same trail as an operator
pressing "send reset link" on day ninety. An **existing** customer added to a second team gets
nothing; they already know how to sign in, and a "set your password" mail would read as a breach
notice.

The **dry run** is not a nicety. The first real use of this screen is somebody typing a customer's
name wrong, and the second is discovering that the owner's address already belongs to an account —
which an operator must be told _before_ a stranger is emailed into somebody else's business.

**One screen, three modules' abilities.** Provisioning is behind `teams.manage`, which `support`
holds, and it calls `GrantPlanAction` and `SetCapabilityOverrideAction`, whose own routes are behind
`billing.manage` and `settings.manage`. Until review caught it, a support operator could POST
`grant_plan=enterprise` with `capabilities_on[]=signals` and hand a tenant an unlimited plan and
feature overrides through a route that does not mention billing at all. `ProvisionTeamRequest` now
**refuses** those fields without the matching ability — refuses rather than strips, because a team
provisioned without the plan the form showed is worse than an error naming the ability needed.

### Announcements, and telling every tenant once (19b)

`AnnouncementBoard::forUser()` is asked on **every tenant page load**, which shapes the whole
implementation: the kill switch short-circuits before any query, the query is one indexed read over a
table holding a handful of rows, and the targeting and dismissals are filtered in PHP because a
`whereJsonContains` against two nullable arrays is neither portable nor indexable.

The copy is per-locale with an English fallback, and the board returns **the locale each line actually
resolved to** so the banner can mark its own `lang` and `dir` — an Arabic reader handed the English
fallback is reading LTR text inside an RTL page, and nothing else on the page knows that.

`AnnounceToTenantsJob` is the one job in the product that touches every tenant, and it is
**aggregated** in the `AnnounceTopLeadsJob` shape: one notification per _team_ through
`NotificationDispatcher::toTeam()`, never a loop over every member of every tenant. Three guards, and
they are not redundant:

- `ShouldBeUnique` on the announcement id — an operator who saves the form twice queues one fan-out.
- `announcements.notified_at` — a retry of a job that **finished** does nothing.
- `announcement_notifications`, a per-tenant claim with a unique index — the case the other two
  cannot cover. This job walks every team, so a crash at team 3,000 of 4,000 means the retry starts
  again at team 1. The insert **is** the claim, so two workers racing a chunk cannot both send, and
  the claim is taken _before_ the send: a crash between the two loses one notification, where the
  other order sends one twice. Telling every customer twice is how the next announcement becomes
  something people filter.

The stored payload carries the **resolved prose**, which is the one documented exception to the
notifications rule that a payload holds keys and params only — see `docs/modules/notifications.md`.

Retiring an announcement sets `ends_at` rather than deleting it — "when did we say the product would
be down?" is a question somebody asks later — and it leaves an already-past date alone rather than
moving the record of what we told people.

### Platform reporting — not tenant reporting with the scope removed (19c)

Reporting's builders are **scoped by design**, and each of their figures has a cohort rule written for one team's window (`reporting-analytics.md`). Running them with the tenant scope removed would not produce a cross-tenant version of the same report — it would silently answer a different question, and there would be no customer to notice. So platform reporting asks its **own** questions, in its own builders.

What it reuses is the discipline and the plumbing, not the Actions:

- `Reporting\Support\DateRange` and its UTC rule, so a window means the same thing on both sides of the product.
- `Ratio::of()`, which returns **null** over a zero denominator — the rule that a `0%` must only ever mean zero.
- `ReportColumn`, `ReportRow`, `Kpi`, `FunnelStep`, `BreakdownSlice` and `ReportCsvExporter`, so one Vue chart set and one CSV writer serve both. `ReportCsvExporter` grew `rowsFor()`/`filenameFor()` — the same writer, given columns and rows directly — rather than a second exporter that would have drifted from the first, and the thing that would have drifted is the formula hardening.

What it does **not** reuse is `ReportKey`: `Admin\Enums\PlatformReport` is its own enum, because a cross-tenant figure must not be reachable through a tenant's one. Adding `margin` to `ReportKey` would have leaked it into `ReportKey::tabular()`, the tenant dashboard's tabs and `/api/v1/reports`' validation rules — all of which a customer reads.

**Thirteen reports**, each a CSV download: growth, the onboarding funnel, revenue by plan, MRR movement, retention by signup cohort, allowance consumption, provider health and spend, AI spend, cost per prospect, and gross margin per tenant, per plan and per signup cohort — plus outreach volume and deliverability. `PlatformReportingTest` asserts the builder produces a table for **every** case, which is what makes "any report is exportable" a closed set rather than a promise.

Each figure's counting rule is `PlatformMetric::definition()`, rendered on screen beside the number and written into the CSV's caption. That is the phase's own risk control made concrete, and it is why `PlatformReportTable` carries `definitions[]` where Reporting's `ReportTable` carries a single `caption`: a tenant report answers one question, and several of these carry five measures whose rules differ.

**Two windows differ from the default thirty days, deliberately.** The audit viewer opens on seven, because `audit_logs` is the busiest table in the product and a thirty-day default would open on a page of last month's noise. The provider-health rates read `admin.reporting.provider_health_days` (seven) of **complete** days, because today has not been rolled up and a part-day would drag every rate towards zero.

### The rollup is a record, not a counter (19c)

`platform_daily_metrics` is `(date, metric, dimension) → value`, and it exists for one reason: **a cross-tenant aggregate over `ai_requests` is the only query in this product with no `team_id` to narrow it.** Every tenant-facing index is scoped by a column that is also the leading edge of its index; the platform's figures are scoped by nothing, so they are answered from a table with one row per day per metric per dimension instead.

It is a **record over the ledgers**, exactly as `usage_meters` is (ADR 0012): nothing in the application increments a value, `PlatformRollup` derives every one of them, and `platform:roll-up --days=30` rebuilds a window. A crashed worker therefore cannot leave the business's numbers _wrong_ — only unwritten, which the backfill fixes.

Four things about it are easy to get wrong, and each has a test:

- **One metric's day is replaced atomically.** `PlatformMetricStore::replaceDay()` deletes the metric's rows for the day and writes the new set in a transaction. An upsert alone would leave yesterday's `google_places` row behind the day Google Places made no calls — and the figure would stay on the screen for ever. Zeros are **written**, not skipped: "no AI calls failed yesterday" and "we have not rolled yesterday up" are different statements.
- **A snapshot must not be summed.** Thirty days of MRR summed is thirty months of revenue. `PlatformMetric::isSnapshot()` decides, and it decides _in the store_, so no builder can collapse a series the wrong way; a snapshot is read from the window's **last populated day**, not from "today" and not from the window's end.
- **The funnel is cohort-shaped, so it is recomputed.** Its rows are dated by the day a cohort _signed up_, and a team that signed up a fortnight ago and runs its first discovery tonight changes a row dated a fortnight ago. Those six metrics are recomputed over a trailing `admin.reporting.funnel_cohort_days` (30) every night rather than written once. Treated as event-shaped, every step after the first would permanently under-report.
- **A backfill will not invent a state nobody recorded.** Dunning, seats, allowance consumption and reported overage are point-in-time: `usage_meters.used` is the current figure for an open period and `subscriptions.stripe_status` is today's status. The command writes them only for a day it is treating as current, and leaves an older day exactly as it found it — saying so in its output rather than leaving an operator to wonder why a backfilled month has no dunning figures.

**The window has to reach a date column as dates, and that is why the store does not call `DateRange::constrain()`.** That method is right for an _instant_ column and wrong here: its upper bound is an exclusive instant, and a `DATE` column compared against `2026-11-01 00:00:00` matches `2026-11-01` on both MySQL and SQLite — so the day _after_ the window would be counted, every time, in the one direction nobody checks. The store converts the bounds to UTC and then to whole days. `PlatformRollupTest` asserts it with a window cut on a **Dubai** clock, which is the other half of the same trap.

Relatedly: **`platform_daily_metrics.date` is deliberately not cast to a date object.** Eloquent writes a date-cast attribute through `fromDateTime()`, which pads it to `Y-m-d H:i:s` — and a padded value fails the inclusive `<= '2026-10-31'` that a bare one passes, so half the rollup would drop out of every window depending on which code path wrote it. One format everywhere: `Y-m-d`.

**Ordering is load-bearing.** Compliance's retention sweep prunes the rows these figures are computed from, and a period that has been swept cannot be recomputed — the same constraint `billing:sync-usage` runs hourly for. `platform:roll-up` is scheduled at **02:40**, ahead of the Signals prune (03:20), Compliance's sweep (03:40) and the insights prune (03:50), and `PlatformRollupTest` asserts the ordering against the real schedule rather than trusting the comment. A later phase moving a sweep earlier fails there instead of silently losing the business's numbers.

The command also walks a backfill **forwards**: MRR movement for a day compares today's per-tenant MRR against the row the previous night wrote, so reversed, the first day would read as an entire platform's worth of new MRR.

### Gross margin per team — the number the business lives on (19c)

What a tenant pays against what its AI and data calls cost us. Both halves have been recorded since Phase 5 — `ai_requests.cost_micros` and `discovery_runs.cost_micros` carry the cost, the plan carries the price — and nothing in the product put them next to each other. **A tenant can be on Scale and still be unprofitable**, and until somebody does, nobody knows which ones are.

It is the one figure assembled from two scales and two currencies, so three rules keep it honest:

1. **Revenue is prorated from the daily snapshots, not taken as MRR.** MRR is monthly; a window is however long an operator chose. Revenue over the window is the sum of the tenant's daily MRR divided by a nominal 30-day month — which also accounts for a plan change mid-window day by day. A 31-day window therefore shows a touch over one month; weighting each day by its own month's length buys a third decimal place nobody acts on.
2. **Cost that cannot be converted is shown, not absorbed.** Provider cost arrives in micro-units of whatever currency the provider billed; `admin.reporting.fx` is a **configured constant**, not a market rate, and the screen prints the rates it used. A currency with no rate is returned as `ConvertedCost::$unconverted` and rendered — at which point every margin on the page is a **ceiling**, and the page says so. That is the phase's own risk note: a margin that looks authoritative while a provider's cost is unrecorded.
3. **Cost with no tenant behind it is its own row.** `ai_requests.team_id` is nullable, so some spend belongs to the platform rather than to a customer. It is reported as `unattributed` and excluded from every tenant row and from the per-plan view, because spreading it would flatter every margin equally and be impossible to notice.

A margin **ratio** is null rather than zero where there is no revenue to divide by. A free-plan tenant costs us money and earns none; "0%" would read as break-even, which is the opposite of true.

Two figures are a floor rather than a number, and both are recorded under **Known limitations** rather than left to be discovered: a plan priced _on application_ (Enterprise) contributes zero to MRR because the contract's real number is not in the system, and `discovery_runs`/`signal_runs` record a cost with no currency column, so theirs comes from `admin.reporting.data_cost_currency`.

### Failed jobs, queues and the schedule (19c)

**The thing Horizon cannot tell you is whose job it was.** Every queued job in this product belongs to a tenant, and the answer is sitting in the serialised payload. `QueueHealth::teamIdFromPayload()` digs it out — **by pattern-matching the serialised string, never by unserialising it.** `unserialize()` on a payload would instantiate whatever classes the string names, which is a remote-code-execution primitive pointed at a table that exists precisely because something went wrong. A regex cannot hurt anybody, and a missed id renders as an em dash rather than a guess.

**Queue depth is driver-dependent and says so.** The `database` driver keeps pending work in a table this can read; Redis and SQS do not, and the screen reports the driver's name and an honest "not readable here" rather than a zero. A queue depth of zero is the single most reassuring number on an operations screen and must never be a default. The oldest-waiting age is the figure that separates a busy worker from a dead one.

**Schedule health is _last seen_, not _last run_.** Laravel stores nothing about past scheduled runs — there is no table, and `schedule:list` prints the next due time, not the last actual one — so "the nightly rollup has not run since Tuesday", the most useful sentence on an operations screen, was a fact nobody was recording. `RecordScheduledTaskRun` writes each run to the **cache** (diagnostic rather than business data, overwritten every run, and a durable table would need a migration and a retention answer). The cost is that a flushed cache reports "never seen", which is why every label says _seen_. A **skipped** run is recorded separately, because `withoutOverlapping()` quietly skipping a stuck overnight job every night afterwards looks exactly like a healthy schedule.

Both sides of that go through one `QueueHealth::commandName()`, and they have to: `Event::$command` carries the PHP binary and the artisan path, quoted by `ProcessUtils::escapeArgument` — single quotes on Unix, **double** quotes on Windows — so a pattern written for one platform silently falls through on the other and the screen reads "not seen" for a command that ran five minutes ago.

Retry and delete key on the **uuid**, not the numeric id: the uuid is what `queue:retry` takes and what survives a retry-and-fail cycle, and a numeric id is reused by the next failure. Retry goes through `queue:retry` rather than reimplementing it — the driver decides how a payload goes back, and a batched job has to be re-registered with its batch. There is deliberately **no transaction** around it: `queue:retry` writes to the queue, and wrapping an external push in one is what CLAUDE.md §2 forbids outright. A **delete** is the other way round — its audit entry is written _before_ the row goes, inside the transaction, because the payload is the only copy of that work and a crash between the two would leave it gone and the trail silent.

### Provider health — advisory by design (19c)

The screen pairs a **live** signal with **recent** context and says which is which: the circuit breaker's state as it is right now, and the error and latency rates from the nightly rollup. A provider that started failing an hour ago therefore shows a healthy rate and an open breaker — the right way round, because the breaker is the live signal and the rates are the context.

Two honest refusals:

- **Three providers have no breaker at all** — the AI transport, the mail transport and Stripe. `PlatformProvider::breakerPrefix()` returns null for them and the screen prints "not instrumented", never "closed". A health panel that reported a green light for something it is not watching would be believed.
- **The breaker is cache-backed and advisory**, by its own design: its state sheds load rather than guaranteeing anything, it evaporates when the cache is cleared, and its failure counter carries the cooldown's own TTL so a quiet provider reads as zero rather than as its history. Every row carries `advisory: true` and the page prints the caveat.

Admin **observes** these breakers; it does not own them. Each provider's prefix and key come from the owning module's own config (`lead_sourcing:cb`, `signals:cb`, `notifications:cb`), because a prefix declared twice is a reset that clears the wrong cache entry and leaves the real circuit open.

The reset calls `CircuitBreaker::reset()` rather than `recordSuccess()`, which does the same thing: an operator resetting a breaker is not recording a success — nothing succeeded — and the method an operations panel calls should not write a small lie into the only place that knows how the provider is doing. It is behind `operations.manage` and audited with whether the circuit was **actually** open, recorded before the reset, because that is what makes the entry worth having.

### The audit viewer, and why reading it is not audited (19c)

A cross-tenant viewer over `audit_logs`, filterable by category, action, actor, tenant, subject and window. **Read-only structurally:** one `GET`, no Action, no update and no delete — here or in the registry's `audit-logs` descriptor — and `PlatformOversightTest` asserts the absence over the whole route table. An audit trail an operator can edit is not an audit trail, and the protection has to be a missing code path rather than a permission somebody could grant.

Two things it does that the registry's index cannot:

- **Categories.** `AuditCategory` groups actions by **prefix**, so impersonation sessions and operator reads are first-class filters rather than four rows in ten thousand you can only find if you already know the action string. The order of the enum's cases is load-bearing: `admin.impersonation.started` and `admin.resource.viewed` both begin `admin.`, so the two specific categories are declared before `AdminWrite` and win. `Other` is the honest catch-all — an unclassified action shows as uncategorised rather than being filed under something that sounds close.
- **A window.** The registry's filters are equality-only by design, and "what did this operator do last Tuesday" needs a range.

**Reading the trail is deliberately not audited.** `AdminAudit` audits reads of tenant data because an operator opening somebody's prospect list is a privacy event; the same rule here would mean every look at the trail wrote a row _to the trail_, which grows without bound and buries the entries somebody came to find.

### The three deferred operator views (19c)

Three earlier phases each deferred an operator view to Phase 19. All three land here, all three are read-only, and in each case the **missing write route is the decision**:

| View                  | Deferred by                            | Why there is no write route                                                                                                                                                                                     |
| --------------------- | -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `signal_runs`         | `signals-plan.md` task 6, `signals.md` | A run spends real money at Serper and on the AI. `TriggerSignalWatchAction` throttles a tenant's own re-runs for that reason, and an operator re-running somebody's watch would spend their allowance for them. |
| Compliance activity   | `compliance-privacy.md`                | An erasure, an export and a retention policy are the **tenant's** decisions as data controller — which is why those routes are on the impersonation blocklist too.                                              |
| Subscriptions and MRR | `billing-plans.md`                     | Covered by platform reporting and the dunning snapshot; the per-tenant billing screen (19b) is where a plan is actually changed, through `SwapPlanAction`.                                                      |

`signal_runs` shows cost, failures and durations per run across tenants; the duration comes from `started_at`/`finished_at` rather than `created_at`, because a queued run can wait minutes before it begins, and a **null** duration is itself the finding on a stuck run.

Compliance activity is a view over `audit_logs` rather than over tables of its own, and deliberately: a retention sweep, an export and an erasure each already write one entry with counts and ids and — equally deliberately — no copy of what was erased or exported. A second activity table would either duplicate those entries or tempt somebody into recording the contents, which `docs/compliance.md` §3.9 forbids. It leads with the **assessments** table, because without a legitimate-interest assessment in force for its market a tenant cannot source at all, and "discovery stopped working" is very often a lapsed row there.

### Outreach oversight and the global do-not-contact list (19c)

**A shared sending domain means one tenant's behaviour is every tenant's deliverability.** A tenant working a bought list raises the complaint rate on a domain every other customer sends from, and the first anybody knows is mail stopping. Platform send volume, bounce and opt-out rates by channel are what make that visible first.

A platform suppression — an address nobody may contact — stays in **`outreach_suppressions` with a null `team_id`**, not a second table (CLAUDE.md §3). That matters more than it sounds: `OutreachGuard` is still the only thing that answers whether a prospect may be approached, `SuppressionList` already includes the **global** scope in every send-time check for every tenant, and a platform list kept anywhere else would be a list the guard does not read. So the enforcement this screen relies on was built in Phase 11 and needed nothing new; `PlatformOversightTest` proves a global entry refuses a send in two different tenants and that the guard, not the screen, is what refuses it.

`AddPlatformSuppressionAction` calls Outreach's own `SuppressionList::suppress()` rather than writing a row, so the value is normalised, hashed and masked exactly like every other entry — a hand-written row would produce an entry that matched nothing, which is a suppression list that silently does not suppress. Only **previews** are shown (`j***@example.com`), because only a hash is stored: a register of people who want nothing to do with us is not a contact book.

Three refusals are built in:

- **No lift route exists**, here or anywhere. `OutreachSuppression::isRemovable()` refuses a global entry, the policy refuses one, and the panel does not offer one; `removable` is rendered on every row — always false — so the absence reads as a rule rather than an oversight. Removing a global suppression would overrule a person's stated wish with a button.
- **Only three of the five reasons are offered.** They asked us to stop, they reported us, or we are adding it by hand. A **bounce** is one tenant's technical fact and an **erasure** belongs to the tenant that received the request; recording either platform-wide would record something that is not true.
- **The note is required**, unlike a team's own entry. A platform entry stops every tenant contacting somebody for ever, and one with no note is one the next operator cannot explain.

### The seeded operator

`SuperAdminSeeder` — `super@admin.com` / `password`, super admin, verified, **in no team and with no `current_team_id`**, which is the point of seeding one rather than promoting a demo user. Registered in `DatabaseSeeder` before `DemoSeeder`. It **refuses to run in production** unless both `ADMIN_SEED_ALLOW_PRODUCTION=true` and `--force`; it refreshes the role on a re-seed and **never resets a password somebody has changed**.

The account has no second factor, so its first `/admin` visit is the enrolment screen. That is correct, and it is in the runbook rather than excepted in the middleware.

None. The panel reads the product's own tables.

## Permissions

Platform roles are a separate axis from `TeamRole`, which is team-scoped by definition — an operator belongs to no tenant, so there is no pivot row to answer from. The mapping lives in `config/admin.php`; `AdminServiceProvider` registers one gate per ability (`admin.<value>`) for every case in the enum, so a new ability cannot be added and left without a gate.

| Ability             | `super_admin` | `support` | `finance` | `read_only` |
| ------------------- | ------------- | --------- | --------- | ----------- |
| `platform.access`   | ✅            | ✅        | ✅        | ✅          |
| `tenant.read`       | ✅            | ✅        | ✅        | ✅          |
| `tenant.write`      | ✅            | ✅        | —         | —           |
| `tenant.delete`     | ✅            | —         | —         | —           |
| `users.manage`      | ✅            | ✅        | —         | —           |

| `billing.manage`    | ✅            | —         | ✅        | —           |
| `settings.manage`   | ✅            | —         | —         | —           |
| `platform.write`    | ✅            | —         | —         | —           |
| `impersonate`       | ✅            | ✅        | —         | —           |
| `audit.read`        | ✅            | ✅        | ✅        | ✅          |
| `reports.read`      | ✅            | ✅        | ✅        | ✅          |
| `operations.manage` | ✅            | ✅        | —         | —           |

**The two Phase 19c abilities are their own, and neither reuses an existing one.**

- `reports.read` — the business's own numbers. Not `tenant.read`, because the figures are aggregates and name **no person**, so reading them is not the privacy event that ability audits; and not `billing.manage`, because they are not only money — putting them there would have hidden the onboarding funnel, the one report that says whether the product works, from everybody except Finance. They are not _anonymous_ either, and the config says so: the margin and per-tenant MRR reports name **companies**, with what each pays and costs. That is commercially sensitive and every operator role can see it; what they never carry is a person's record.
- `operations.manage` — retry or drop a failed job, reset a breaker, add to the global do-not-contact list. Not `settings.manage`, because these are **incident** actions: whoever is on support at 2am needs them and does not need the Stripe switch. Not `tenant.write`, because none of them is a tenant's record — each reaches every tenant at once, which is why each is audited with no team and the operator's name. Read-only deliberately does not hold it: looking, not touching.

**Two abilities are checked on every resource route, not one.** The route declares a generic one (`tenant.read`, `tenant.write`, `tenant.delete`) and the descriptor declares its own through `AdminResource::ability()`; an operator needs both. That exists because the route ability is necessarily broad — `tenant.write` means "fix a customer's record" — and two resources are **not** a customer's record:

- `audit-logs` → `audit.read`. It is other operators' actions as well as customers'.
- `ai-prompt-templates` → `platform.write`, **super admin only**. The prompt registry is ours, and an edit lands in _every_ tenant's next AI call. Behind `tenant.write` alone, a support engineer could rewrite the system prompt for the whole platform from a screen meant for correcting a company name. `AdminRouteContractTest` pins the list of overrides, so adding or dropping one is a failing test rather than a quiet diff.

**Account operations on another operator are super-admin only** (`Admin\Support\ProtectsOperators`). `users.manage` is the support engineer's ability, and every operation behind it is safe to do _for a customer_ while none of them is safe to do _to a colleague with more power_: clearing a super admin's second factor leaves `EnsureAdminTwoFactor` sending them to re-enrol — a lower role taking the second lock off a higher one — and revoking their sessions and tokens is a denial of service against the one person who would notice.

**404 for a non-operator, 403 for an operator without the ability.** A 403 on the door confirms there is something behind it; a 404 says what a wrong URL says. Once an operator is inside, they already know the panel exists, so a 403 is the honest answer about _this_ screen.

**Two-factor authentication is required** (`ADMIN_REQUIRE_TWO_FACTOR`, default on). One super-admin credential reads every tenant's data in the product; a password alone is not the right lock. The switch exists so a test suite and a first walk through the panel do not have to solve a TOTP challenge — it is not a deployment option, and Phase 20 should assert it on in production.

## Known limitations / TODO

- **No user deletion.** Deliberately deferred, not forgotten: deleting a platform user who is a team's last Owner needs a product decision (is the team deleted, transferred, or is the delete refused?), and the panel can already remove a member from a team, suspend a tenant, and erase a _data subject_ through Compliance. The self-service account delete (`ProfileController::destroy`) is untouched.
- **Phase 19b** owns the platform settings store, the global and per-team Stripe switches, plan grants with bespoke allowances, plan-driven capabilities over Pennant, `ProvisionTeamAction`, announcements, and the `payment_failed` and `assessment_review_due` notification types.
- **Filters on a registry index are equality-only, over a declared option list.** A **window** exists where it is needed — platform reporting, the audit viewer, compliance activity and signal runs all take one (`PlatformWindowRequest`) — but the forty generic indexes do not, because there a range is a scan rather than an aggregate.
- **The team picker is capped at 500 tenants** on a registry index and in the audit viewer. Past that an operator filters by passing `team_id` in the query string, which both accept directly. A searchable picker is still a nicety.
- **Two platform money figures are a floor, not a number**, and both are visible rather than hidden:
    - A plan priced **on application** (Enterprise) contributes **zero** to MRR, because the contract's real number is not in the system — a grant carries allowances, not a price. `PayingTeams` and `TeamPaying` are what stop such a tenant disappearing from the revenue and retention reports entirely.
    - `discovery_runs` and `signal_runs` record `cost_micros` with **no currency column**, so theirs comes from `admin.reporting.data_cost_currency`. The right fix is a currency column on both tables; until then a deployment that changes provider currency changes that key.
- **Only the margin reports split cost by currency.** `TeamCostMicros` carries it in the dimension, so the margin rows can honour the never-absorb-an-unknown-currency promise one row at a time. The cost, AI-cost and lead-cost reports aggregate across whatever the ledger held and convert at the configured rate for the source — exact while each ledger bills in one currency (today's case: `ai-platform.cost.currency` is a single value) and wrong if one ever bills in two.
- **The exchange rate is a configured constant, not a market rate** (`admin.reporting.fx`), and every money screen prints the rates it used. A live FX call inside a nightly rollup, for a figure whose third significant digit nobody acts on, was the alternative.
- **Three figures are honest but blunt.** "Ceilings hit" counts per metric, so a tenant out of both leads and credits counts twice (the label says so, and the pricing report breaks it down). The AI latency mean divides by **all** calls, cache hits and failures included. Provider health's rates are the last seven **complete** days from the rollup, so a provider that started failing an hour ago shows a healthy rate next to an open breaker — which is the useful pairing, not a contradiction.
- **Schedule health is _last seen_, not _last run_.** Laravel stores nothing about past scheduled runs, so the panel records them in the **cache**; a flushed cache reads as "not seen" rather than as a missed run. A durable table would need a migration and a retention answer for something whose whole value is the last line.
- **`platform_daily_metrics.date` is not cast to a date object**, and that is load-bearing rather than an oversight: Eloquent would write a date-cast attribute padded to `Y-m-d H:i:s`, and a padded value fails the inclusive `<= '2026-10-31'` that a bare one passes — so half the rollup would drop out of every window depending on which code path wrote it.
- **`platform:roll-up` has no catch-up of its own.** It rolls up yesterday; a night the scheduler missed is closed with `--days`. The movement figures survive a gap regardless, because the baseline is the last day actually recorded rather than "yesterday" — but a missing day's _flows_ are gone once the sweeps have pruned the ledgers behind them.
- **`queue:retry all` runs synchronously inside the web request.** Fine for the handful of rows an operator is looking at, and the wrong shape for a backlog of thousands. Phase 20 did **not** change this — it wired Pulse (and put it behind this panel's own door, see below), which gives an operator the depth and the rate of a retry storm but not a better place to run one from. Dispatching the retry as a job remains the right answer and is still open.
- **`perCohort` and the retention report load every tenant**, chunked where it matters. Correct at MVP scale, worth revisiting alongside the MySQL index pass.
- **A trap worth knowing, found here and fixed here:** `$this->seed(SomeSeeder::class)` in a test returns a `PendingCommand` that only runs when it is **destructed**, so an exception the seeder throws never reaches the assertion count. `DemoSeeder` had been unable to run at all for that reason. Use `$this->seed()` only when the test then asserts on what the seeder produced; to assert that a seeder _runs_, invoke it directly, as `tests/Feature/Core/DatabaseSeederTest` does.
- **MySQL indexes for the cross-tenant indexes are unproven.** The suite runs on SQLite, which says nothing about whether a query plan holds — the standing caveat for this repo. Worth a pass with production-shaped data during Phase 21.

## Signals, after S7

Two registry details changed when signal types became rows a tenant owns (ADR 0018), and
both are consequences of this panel being **cross-tenant**:

- **`signals`' event filter is built from `SignalPresetCatalogue::labels()`**, not from any
  team's library. There is no "the" set of event types any more; the platform presets are
  the keys every tenant shares, which makes them the only ones an operator can usefully
  filter the whole table by. A tenant's own key is reachable through search. Read from the
  catalogue rather than the database, so a registry definition stays a declaration and not a
  query.
- **`signal-watches` no longer shows which types a watch watches for.** A registry column
  reads a column or an eager-loaded `relation.attribute`, and the types are now a count over
  a pivot — neither. Teaching the registry `withCount` for one read-only detail panel is more
  machinery than the answer is worth, and `/admin/signals` already shows each signal's own
  `event_key`, which is the question an operator actually asks.
